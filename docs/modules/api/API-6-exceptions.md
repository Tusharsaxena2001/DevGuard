# API-6 Exceptions / approvals (apps/api)

**Responsibility:** request, decide, validate and expire destination exceptions (ADR-007).
**Depends on:** API-4, API-5.

## Contract
- `POST /exceptions` (device or user): {projectId, destination, reason, eventId?}; destination normalized; creates `pending`.
- `GET /exceptions` (scoped; filter by status), `GET /exceptions/:id` with decision history.
- `POST /exceptions/:id/approve` {reason, expiresAt}, `POST /exceptions/:id/reject` {reason}, `POST /exceptions/:id/revoke` — approver role in project or admin; approver != requester (403); `expiresAt` must be future and <= cap.
- `POST /agent/exceptions/validate` (device auth) {project, destination}: uses `validateException` from policy-engine with server time; returns `{valid, exceptionId?, expiresAt?, approverId?}`.
- Expiry enforced at validation time (no reliance on a cron); optional sweeper marks `expired`.
## Acceptance
Self-approval blocked; non-scoped approver blocked; wrong destination/project invalid; expired and revoked invalid; boundary time test; every state change audited; client-supplied approval claims ignored.

## Implemented (apps/api)
- **Scope (ADR-014):** deciding is admin-only (`security_admin`, global). There are no project-scoped approvers. Requesting needs the requester to be an employee assigned to the project (an admin who is not assigned cannot request, which keeps requester != approver meaningful and testable with the two seeded admins).
- **Routes** (`/v1`): `POST /exceptions` (user session) and `POST /agent/exceptions` (device): body `ExceptionRequestInput` `{projectId, destination, reason >= 10 chars, eventId?}`; `GET /exceptions` (admin: all, others: own; filters `status`, `projectId`, paging), `GET /exceptions/:id` (admin or requester, else 404) with the decision history; device equivalents `GET /agent/exceptions[/:id]` (own only); `POST /exceptions/:id/approve` `{reason, expiresAt}`, `/reject` `{reason}`, `/revoke` `{reason}` (admin); `POST /agent/exceptions/validate` `{projectId, destination}` (device).
- **Request rules:** the destination is normalised by the policy engine (a destination that does not parse is 400); the project must exist (404) and the requester be assigned (403); `eventId`, if given, must be one of the requester's own events (400); one pending request per requester per project + destination (409) and at most 20 pending per requester (409).
- **Decision rules** (one transaction with the audit row): approve and reject need the request to be `pending`, revoke needs it `approved`; the status change is `UPDATE ... WHERE status = <expected>` so two admins cannot both decide (409 for the loser); **approver != requester** (`self_approval_forbidden`, 403, for approve and reject); `expiresAt` must be in the future and within `EXCEPTION_MAX_TTL_HOURS` (default 72, 400 otherwise). History rows are append-only.
- **Validation** (`POST /agent/exceptions/validate`): uses only server records and the server clock; returns `{valid, exceptionId, expiresAt, approverId, requesterId, waivedRuleIds}`. Valid only if: the device owner is the requester, still assigned to the project, the exception is `approved` for exactly this project + normalised destination (exact host and repo path, no sub-paths or lookalikes), the latest approval has not expired, and the policy engine's `validateException` agrees (which also refuses approver == requester). The longest-lasting valid one is returned. **Waivers are always empty**: an exception covers the destination only, never secrets or prohibited files (ADR-007). Unknown fields in the body (`valid`, `approved`, ...) are 400: client claims are not an input.
- **Expiry** is evaluated on read and on validation (`expired` is a derived status); there is no background job. The `expired` and `approved` filters are applied after reading (both are stored as `approved`).
- **Audit** (actor, same transaction): `exception.requested`, `.approved`, `.rejected`, `.revoked` with project, destination, requester and (approval) expiry. Reasons are not copied into the audit summary; they live in the history rows.
- **Contract additions** (`packages/shared`): `ExceptionEntry`, `ExceptionDecisionEntry`, `ExceptionQuery`, `ExceptionPage`; `ExceptionValidationResult.requesterId`. Migration `exception_lookup_index`.
- **Tests:** `test/exceptions.e2e.test.ts` (request rules, self-approval for approve and reject, non-admin 403, expiry validation and cap, double decision and concurrent approval, revocation, every scope mismatch, unassigned requester, expiry by the server clock including a boundary test, a self-approved row forced into the database, client approval claims, credentials, reading and filters).
- **Security review:** independent read-only review found no critical/high issues and no way to push to an unapproved destination without an approval by a different admin within scope and expiry. Fixed: the approver must still be an active security admin **when the approval is used** (a demoted or disabled approver's approvals stop working); pending-request spam and duplicates cannot be raced (advisory lock per requester + partial unique index `ExceptionRequest_one_pending_per_scope`); an unknown and an unassigned project both answer 403 on request (no project-id probe); the `approved` and `expired` list filters are done in the database (correct totals and paging). Accepted: the agent trusts the server's scope answer (server URL is https or localhost; the engine re-checks expiry and approver != requester locally); the requester's `reason` is free text that a dashboard must render as text, never as HTML.
- **Known gaps:** an approval is valid for every push until it expires (it is not single-use); a validation answer can go stale between the check and the push (seconds); admins can approve for any project (ADR-014); reasons are free text shown to admins and, sanitised, to the requester.
