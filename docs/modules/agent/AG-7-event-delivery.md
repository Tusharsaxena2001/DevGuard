# AG-7 Event delivery (apps/agent)

**Responsibility:** build minimal, redacted security events and deliver reliably.
**Depends on:** AG-5, API-5.

## Contract
- Event = SH-1 `SecurityEventInput` (timestamp, project id, destination host/repo, operation, refs, decision, rule ids, mode, outcome, correlation id, policy version, exception ref). Built only from `Decision` + metadata; no content.
- Delivery: POST with device auth; on failure append to `spool/` (bounded size, oldest dropped with a counter); retry on next command/push. Delivery failure never changes push decision.
- Same correlation id shown to the developer in the block message.
## Acceptance
Schema-strict (extra fields rejected), spool and replay, idempotency key prevents duplicates, no secret/content in event or logs (fixture with synthetic secret asserted absent).

## Implemented (apps/agent)
- **Flow:** every push decision is recorded twice by a tee sink (`adapters/tee-event-sink.ts`): the local append-only `events.jsonl` (unchanged) and the delivery spool. After the hook has printed its message and set the exit code, it tries to deliver the spool with the short-timeout client (3 s, one attempt). `devguard sync` also delivers after a successful sync ("retry on the next command"). Delivery failure of any kind leaves the spool as it was and never changes a decision or the exit code.
- **Spool** (`adapters/fs-store/fs-event-spool.ts`, port `ports/event-spool.ts`): `<home>/spool/<occurredAt ms>-<idempotencyKey>.json`, one strict `SecurityEventInput` each (0600, atomic writes, directory 0700 and trust-checked like the rest of the state). Oldest first. Bounded at 1000 events: when full the oldest are removed and counted in `spool-dropped.json`; a damaged or forged entry is discarded and counted too, so it cannot block the queue. The count is never reset, so loss stays visible. Unsafe keys are refused.
- **Delivery** (`use-cases/deliver-events.ts`): up to 50 events and about 900 kB per request, at most 5 requests per run. A key leaves the spool when the server has answered for it (`accepted`, `duplicate`, or `rejected` = final); a failed request, or events the server did not answer for, stay queued. A reply that covers nothing that was sent stops the run (no spinning). Redelivery is safe: the server de-duplicates by key.
- **API client:** `sendEvents` (`POST /v1/agent/events`) validates the reply with the shared `EventBatchResult` schema and retries transient failures when not in the hook.
- **Reference shown to the developer:** the correlation id printed as `Reference:` in the block message is the event's `correlationId`, so an admin can find the event with `GET /events?correlationId=...` (tested end to end).
- **Status:** `devguard status` shows `Pending events: N` and how many were lost to a full or damaged queue.
- **Tests:** spool adapter (order, bounds and drop count, forged/corrupt entries, permissions, unsafe keys, no content fields), delivery use case (answers, failures, partial answers, batch and byte limits, no secret in outcome), tee sink, client `sendEvents`, and real-hook e2e against a stub API in its own process (event arrives with the device credential and the displayed reference, no secret value in the request body, an outage leaves the decision unchanged and the event is delivered by the next push, status shows the queue); plus a manual run against the real API.
- **Security review:** independent read-only review found no critical issues. Fixed: one event the server refuses outright can no longer stall the queue (a refused batch is retried event by event, and only the offender is discarded); events the server refuses are no longer reported as delivered: they are discarded, **counted in the lost counter** and reported as "refused"; the hook delivers at most one batch so a backlog never delays a push (the rest goes with `devguard sync` or later pushes). Accepted and documented: `refs` and finding paths are client text and are not scanned; `outcome`, `wouldBlock` and `exceptionId` are agent-reported (a stolen device secret can forge them, ADR-006), so a UI must not present them as verified.
- **Known gaps:** events refused by the server (the owner is no longer assigned to that project) survive only in the local `events.jsonl`; `events.jsonl` has no size limit or rotation (pre-existing, AG-3); a local user can delete queued events (ADR-006); the spool is not encrypted; an unenrolled device queues events that are only delivered after it enrolls (and may be dropped if the queue fills first).
